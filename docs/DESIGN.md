# 仕組みと設計

このツールが「なぜその挙動なのか」を説明します。実際の運用手順は
[OPERATIONS.md](OPERATIONS.md)、フラグの一覧は [USAGE.md](USAGE.md) を参照してください。

## 全体の流れ

```
起動
 ├─ 引数検証 (--size XOR --usd、--trigger-price には --trigger-when 必須)
 ├─ /info meta 取得 → 銘柄検証 + asset_index / szDecimals 解決  ← 未知銘柄はここで停止
 ├─ [本番のみ] HL_AGENT_PK から署名器を構築 + アドレス照合
 ├─ [本番のみ] /info userRole 照会 → master アカウント解決     ← 未登録はここで停止
 └─ /info l2Book (鮮度チェック付き) → 初期 mid

トリガー待ち
 └─ 価格条件 OR 経過時間 のいずれか先に成立した方で発火 (両方未指定なら即時)

サイジング (発火直後)
 ├─ --usd なら発火時 mid で枚数に換算
 ├─ 1 スライス量を szDecimals へ切り捨て → 合計を再計算
 └─ 1 スライスがゼロ / 最低名目金額割れなら停止

スライスループ (i = 1..slices)
 ├─ 経過時間 >= duration なら打ち切り (最終スライスも例外なし)
 ├─ /info l2Book (鮮度チェック) → 指値価格を計算
 ├─ 最低名目金額を実注文価格で判定 → 割れていれば skip して次へ繰越
 ├─ IOC 発注 (1 回のみ送信) → 応答を解析
 │   ├─ filled → 約定量と平均価格を加算
 │   ├─ resting → cancel → orderStatus で実約定量を確定
 │   ├─ error → 即時ハードストップ
 │   └─ 送信失敗 (結果不明) → cloid で照合して再送 or 停止
 └─ 次スライスの期限まで待機

最終レポート
```

## トリガー

価格トリガーと時間トリガーは **OR (先に成立した方が勝ち)** です。

| 指定 | 挙動 |
|---|---|
| `--trigger-price` + `--trigger-when` のみ | 価格条件が成立するまで無期限に待機 |
| `--start-after` のみ | 単純な遅延開始。板のポーリングは行いません |
| 両方 | 先に成立した条件で開始 |
| どちらもなし | 即時開始 |

どちらの条件で発火したかはログに明示されます (`Triggered: price above 40 (mid=40.12)` など)。

### `--trigger-when` を必須にした理由

起動時の mid から `above` / `below` を自動推定する設計も検討しましたが、採用しませんでした。
起動の一瞬にヒゲやノイズがあると、ユーザーの意図 (例: ブレイクアウト買い = `above`) と
逆の条件が設定され、**コマンド実行直後に意図しない発火**を起こすためです。
`--trigger-price` を指定する場合は `--trigger-when` の明示を必須とし、省略はエラーにしています。

### ポーリング中の通信エラー

`/info` の通信エラーはクライアント内で再試行され、それでも失敗した場合はループが次の
ポーリングで再挑戦します。ただし **5 回連続で失敗するとハードストップ**します。
トリガーが実質的に機能していない状態で無言のまま待ち続けることを防ぐためです。

## サイジングと丸め

### 枚数の確定

1. `--usd` 指定の場合、発火時点の mid で枚数に換算します
2. 1 スライスあたりの量を銘柄の `szDecimals` へ**切り捨て**ます
3. 切り捨て後の 1 スライス量 × スライス数を、実際の目標量 (adjusted) とします

1 スライスを先に丸めてから掛け戻すのは、Hyperliquid が受け付けないサイズ
(例: `0.74625 HYPE`) を毎回送ってしまうのを避けるためです。切り捨てなので、
目標量を超過することは構造的に起こりません。

### 価格の丸め

Hyperliquid の価格グリッドは「有効数字 5 桁以下」かつ「小数点以下 `6 - szDecimals` 桁以下」です。
本ツールはこれに加えて**方向**を制御しています。

- **ロングは切り上げ (ceil)**
- **ショートは切り捨て (floor)**

四捨五入や一律切り捨てにすると、丸めた結果の指値がベストアスク/ベストビッドを跨げなくなり、
IOC 注文が板に届いた瞬間に不発 (即時キャンセル) になります。約定性を維持する方向へ倒しています。

また、ワイヤ形式へ変換する際は末尾のゼロを除去します (`2387.0` → `2387`)。
これは親リポジトリで実際に `badAloPxRejected` を踏んだ実績にもとづく処理です。

### 最低名目金額 ($10) の判定

Hyperliquid には約 $10 の最低名目金額があります。この判定は **mid ではなく実際の注文価格**
に対して、1% の余裕をもたせて行います。

ショートの場合、テイカー指値は mid **より下**に置かれます。mid 換算でちょうど $10.00 になる
サイズが、実際に取引所へ届く価格では $9.96 になり、致命的な `MinTradeNtl` 拒否として
返ってくる — これを実価格で判定することで、全体停止ではなく「そのスライスを skip して繰越」
という軽い処理に変えています。

起動前の検証で 1 スライスがゼロまたは最低金額割れになる場合は、何も送信せずに停止します。
執行中に価格が動いて割れた場合は skip して次スライスへ繰り越します (目標量は累積値なので
繰越は自動的に行われます)。最終スライスでも割れている場合、その残余は本質的に執行不能なので
警告として報告します。

### 丸め落ちは必ず報告する

1 スライスを切り捨てる以上、adjusted 合計が要求量を下回ることがあります。
`szDecimals` が粗い銘柄では差が大きくなります (例: 整数単位の銘柄で 10.5 を 3 スライス
→ adjusted 9)。

adjusted 目標を満たしていれば「完了」ではありますが、単独の `complete` は表示しません。
`complete (against the adjusted target)` と表示し、次の行を必ず添えます。

```
NOTE:            rounding dropped 1.5 of requested 10.5 at pre-flight
```

この NOTE は部分約定や中止の場合にも表示されます。丸め落ちの事実は結果によらず変わらないためです。

## スライスループ

### キャッチアップ方式

各スライスの目標は**累積値**です。

```
target_at_slice(i) = per_slice × i     (最終スライスは adjusted 合計そのもの)
今回の発注量        = target_at_slice(i) − これまでの約定量
```

前のスライスが約定不足だった分は、次のスライスの発注量に自動的に上乗せされます。
逆に約定が先行している場合は発注量がゼロになり、そのスライスは何も送りません。
最終スライスの目標を adjusted 合計に固定することで、丸めの端数もすべて吸収されます。

### 執行ウィンドウは厳格

`--duration` が経過した後は、**最終スライスであっても**注文を出しません。

再試行・板の再取得・約定量の確定処理で遅延は蓄積します。そして最終スライスはキャッチアップ
により、それまでの不足分をすべて背負った**最大サイズ**になりがちです。ここだけ例外にすると、
「その回で最も大きい注文が、指定ウィンドウから最も遠く外れて発火する」という最悪の組み合わせに
なります。期限に達した実行は停止し、未執行分を報告します。通常の実行では最終スライスは
ウィンドウ内に収まります。

### 板の鮮度

各スライスの直前に `/info l2Book` を取得し、`--max-book-age-ms` (既定 3000ms) より
古ければ再取得します (1 秒間隔で 3 回まで)。それでも古い場合はハードストップします。
起動直後のサイジングにも同じ鮮度ゲートを適用しています。

なお、板のタイムスタンプがローカル時刻より**未来**の場合は「新鮮」として扱います。
軽度のクロックずれを許容するためです。

## エラー処理

最も重要な区別は次の 3 つです。

| 種類 | 挙動 | 理由 |
|---|---|---|
| `/info` の通信エラー | 指数バックオフで再試行 (1s → 2s → 4s) | 読み取り専用なので再試行のコストがない |
| `/exchange` の通信エラー | **再試行しない**。cloid で照合して復旧 | nonce により注文は冪等ではない (後述) |
| 取引所の拒否 | **再試行せず即時停止** | 取引所は既に判断を下している。再送は二重約定のリスク |

### 曖昧な送信の照合 (`/exchange` reconciliation)

注文は nonce に対して署名され、Hyperliquid は本文を受け取った時点で nonce を消費します。
つまり `POST /exchange` が **HL に届いた後**で失敗した場合 (タイムアウト、応答の消失)、
同じ署名済み本文を再送しても nonce 切れで拒否されるだけで、しかも元の注文は約定している
かもしれません。素朴な「3 回再試行」では、実際には約定した注文を「失敗」と報告してしまいます。

そこで `/exchange` へのリクエストは **1 回だけ送信**し、**cloid を冪等キー**として復旧します
(cloid は署名前に自分で決めるため、応答が失われても手元に残ります)。

1. 曖昧な失敗が起きたら、master アカウントで `/info orderStatus` に cloid を照会する
2. **HL が注文を持っている** → その状態を採用。再送はせず、約定は 1 回だけ計上する
3. **`unknownOid` が返る** → 注文は届いていないので、**新しい nonce で再署名**して再送
   (最大 2 回まで。毎回、再送前に照合を挟む)
4. **照合自体が失敗し続ける** → 停止し、結果が不明であることを明示する。
   どちらかに決め打ちすると二重約定のリスクがあり、それは取り消せない

cancel の失敗は致命的ではありません。その後の `orderStatus` 照会が真実を確定させるためです。

### 終端ステータスのみを採用する

約定量として採用するのは **終端ステータス** (`filled`, `canceled`, `rejected` など) のときだけです。

`open` のままの注文は次の 1 ミリ秒で追加約定しうるため、その時点の部分約定数を最終値として
採用すると約定量を過小に見積もり、以降のすべてのスライスが**過剰発注**になります
(キャッチアップが「まだ足りない」と誤認するため)。`open` の場合は再試行を続け、
それでも終端に至らなければ安全側に倒して停止します。

### IOC が板に残った場合

IOC 注文が想定外に板に残った (resting) 場合は、キャンセルした上で `/info orderStatus` を
照会し、実際に何枚約定したかを確定させます。このとき約定価格は**指値ではなく HL が報告する
`avgPx`** を採用します (指値は「最悪の価格」なので、平均価格レポートが歪むため)。

約定量を確定できない場合は推測せずに停止します。ゼロと仮定すると次のスライスで過剰発注に
なり、超過ポジションは取り消せないためです。

### 拒否メッセージの分類

Hyperliquid は構造化されたエラーコードを返さず、自由文のメッセージを返します。
本ツールは代表的なものを部分文字列で分類し、対処可能なメッセージに変換します。

| 分類 | 判定キーワード (大文字小文字を無視) | 表示 |
|---|---|---|
| 証拠金不足 | `insufficient margin` | 入金するか `--usd`/`--size` を減らしてください |
| 最低名目金額割れ | `mintradentl`, `minimum` | `--usd`/`--size` を増やすか `--slices` を減らしてください |
| 未分類 | 上記以外 | HL の生メッセージをそのまま表示 |

分類できなかった場合も**停止する点は同じ**です。分類は原因究明を助けるためのものであり、
安全性の判断には使っていません。

## userRole 照会によるマスター解決

本番実行時 (ドライランでは行いません) の起動時に、`HL_AGENT_PK` から導出したアドレスで
`/info userRole` を照会します。目的は 2 つです。

1. **未登録の鍵を早期に検出する** — Hyperliquid は認可されていない API ウォレットからの
   署名アクションを拒否します。最初の注文で判明するより、起動時に止まる方が安全です
2. **マスターアカウントを解決する** — HL は Agent の注文を**マスター配下**に記録するため、
   `/info orderStatus` はマスターアドレスで照会する必要があります。Agent のアドレスで
   照会すると、実在する注文に対して `unknownOid` が返ります。約定量の復旧処理はこれを
   「約定ゼロ」と誤読し、以降のすべてのスライスで過剰発注してしまいます

実際の mainnet API で応答形状を確認済みです。

```
POST /info {"type":"userRole","user":"<agent_addr>"}
  → {"role":"agent","data":{"user":"0x<master>"}}

POST /info {"type":"userRole","user":"<master_addr>"}
  → {"role":"user"}

POST /info {"type":"orderStatus","user":"<master>","oid":<未知>}
  → {"status":"unknownOid"}
```

照会結果が `agent` 以外だった場合は、確認できた role を表示して起動を中止し、何も送信しません。

## EIP-712 署名

署名コア (`src/eip712.rs` / `src/signer.rs`) は親リポジトリ `diff-old-new/executor` から
**そのまま移植**したものです。Hyperliquid Python SDK に対してバイト単位でクロスチェック済みで、
その検証ベクタ (10 件) も一緒に移植しています。

重要な性質:

- msgpack は**名前付きマップ**でシリアライズします (`rmp_serde::to_vec_named`)。
  配列形式にすると action_hash が変わり、署名が無効になります
- 構造体の**フィールド順序が意味を持ちます**。並べ替えると署名が壊れます
- EIP-712 ドメインは mainnet / testnet で同一です (`chainId=1337`, `verifyingContract=0x0`)。
  ネットワークの違いは `Agent.source` の `"a"` / `"b"` だけで表現されます
- `--network` はエンドポイント URL と `Agent.source` を**同時に**切り替えるため、
  両者が食い違うことは構造的に起こりません

詳細は [DEVELOPMENT.md](DEVELOPMENT.md) を参照してください。
