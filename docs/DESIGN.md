# 仕組みと設計

このツールが「なぜその挙動なのか」を説明します。実際の運用手順は
[OPERATIONS.md](OPERATIONS.md)、フラグの一覧は [USAGE.md](USAGE.md) を参照してください。

## 全体の流れ

```
起動
 ├─ 引数検証 (--size XOR --usd、--trigger-price には --trigger-when 必須)
 ├─ /info meta 取得 → 銘柄検証 + asset_index / szDecimals 解決  ← 未知銘柄はここで停止
 ├─ [本番のみ] HL_AGENT_PK から署名器を構築 + アドレス照合
 ├─ [本番のみ] /info userRole 照会 → master アカウント解決     ← 未登録はここで停止
 └─ 時間のみトリガー (--start-after のみ、価格条件なし) 以外は
    /info l2Book → ValidatedMarketSnapshot で検証済みの初期 mid をログ出力
    (時間のみトリガーは締切まで l2Book を一切呼びません)

トリガー待ち
 └─ 価格条件 OR 経過時間 のいずれか先に成立した方で発火 (両方未指定なら即時)
    価格条件のポーリングは毎回 ValidatedMarketSnapshot で検証する

サイジング (発火直後)
 ├─ --usd なら発火時点のスナップショットで枚数に換算
 │   ├─ 価格トリガーで発火した場合: トリガーを満たしたスナップショットをそのまま再利用 (再取得しない)
 │   └─ 即時開始 / 時間のみトリガーの場合: サイジング直前に新規取得した pre-flight スナップショットを使う
 ├─ 1 スライス量を szDecimals へ切り捨て → 合計を再計算
 └─ 1 スライスがゼロ / 最低名目金額割れなら停止

スライスループ (i = 1..slices)
 ├─ 経過時間 >= duration なら打ち切り (最終スライスも例外なし)
 ├─ /info l2Book → ValidatedMarketSnapshot で検証 → 指値価格を計算
 ├─ 最低名目金額を実注文価格で判定 → 割れていれば skip して次へ繰越
 ├─ IOC 発注 (1 回のみ送信) → 応答を解析
 │   ├─ filled → 約定量と平均価格を加算
 │   ├─ resting → cancel → orderStatus で実約定量を確定
 │   ├─ error → 即時ハードストップ
 │   └─ 送信失敗 (結果不明) → cloid で照合して再送 or 停止
 └─ 次スライスの期限まで待機

最終レポート
```

## トリガー

価格トリガーと時間トリガーは **OR (先に成立した方が勝ち)** です。

| 指定 | 挙動 |
|---|---|
| `--trigger-price` + `--trigger-when` のみ | 価格条件が成立するまで無期限に待機 |
| `--start-after` のみ | 単純な遅延開始。板のポーリングは行いません |
| 両方 | 先に成立した条件で開始 |
| どちらもなし | 即時開始 |
| `--expire-after` 併用 | 期間内にどのトリガーも成立しなければ、何も発注せず終了 (exit code 3) |

どちらの条件で発火したかはログに明示されます (`Triggered: price above 40 (mid=40.12)` など)。

### `--expire-after`: 不発時に発注せず終了する打ち切り (Issue #8)

`--start-after` が「フォールバック**開始**」(期限が来たら価格未達でも TWAP を強制開始する)
であるのに対し、`--expire-after <duration>` は待機フェーズそのものの**打ち切り**です。
期間内にどのトリガー条件も成立しなければ、**何も発注せずに**プロセスを終了します。

- 未指定時: 従来どおり無期限待機 (後方互換)。
- 期限切れ時: 標準出力に `EXPIRED: no trigger fired within <dur>` を出力し、**exit code 3**
  で終了します (`0`=完了 / `1`=中止 / `2`=引数エラー / `3`=期限切れ)。`TwapReport` は
  出力されません (TWAP を開始していないため)。
- **同一 tick での優先順位はトリガーが勝つ**: 各イテレーションは時間条件→価格条件を評価した
  「後」に expiry を評価します。期限ちょうどの tick で価格条件も成立していれば、トリガーが
  優先して発火します (expiry は両トリガーとも不成立だった場合にのみ成立します)。
- 時計基準: `--start-after` と同じ monotonic clock (`tokio::time::Instant`)。待機開始と
  同一の起点から計測し、プロセスのサスペンド中は進みません。
- バリデーション (起動時 fail-fast、ネットワーク到達前):
  - `--expire-after 0s` はエラー。
  - `--start-after` 併用時、`expire_after <= start_after` はエラー (start が必ず先に
    発火し expire に到達できないため)。
  - トリガー未指定 (即時開始) との併用もエラー (即時開始に期限は無意味なため)。

### `--trigger-when` を必須にした理由

起動時の mid から `above` / `below` を自動推定する設計も検討しましたが、採用しませんでした。
起動の一瞬にヒゲやノイズがあると、ユーザーの意図 (例: ブレイクアウト買い = `above`) と
逆の条件が設定され、**コマンド実行直後に意図しない発火**を起こすためです。
`--trigger-price` を指定する場合は `--trigger-when` の明示を必須とし、省略はエラーにしています。

### ポーリング中の通信エラー

`/info` の通信エラー (空板で mid が取得できない場合を含む) はクライアント内で再試行され、
それでも失敗した場合はループが次のポーリングで再挑戦します。連続失敗の判定は **回数ではなく
時間**で行い、`--wait-network-grace` (既定 30 分) を超えて連続失敗が続いた場合にのみ
ハードストップします。計測は最初の失敗時刻からの経過時間 (`tokio::time::Instant`) で行い、
1 回でも成功すればリセットされます。中止時のメッセージには失明していた継続時間と最後の
エラーを含めます。待機フェーズはポジションも未決注文も持たないため、通常のネットワーク瞬断
程度は許容できる — とはいえ無期限に無言で待ち続けることは避けるため、5 分毎に info レベルの
heartbeat ログを出します。価格トリガー待機では現在の mid・閾値との乖離・経過時間を含み、
`--start-after` のみの時間トリガー待機ではネットワークに一切触れず経過/残り時間のみを
報告します。

## サイジングと丸め

### 枚数の確定

1. `--usd` 指定の場合、発火時点の mid で枚数に換算します
2. 1 スライスあたりの量を銘柄の `szDecimals` へ**切り捨て**ます
3. 切り捨て後の 1 スライス量 × スライス数を、実際の目標量 (adjusted) とします

1 スライスを先に丸めてから掛け戻すのは、Hyperliquid が受け付けないサイズ
(例: `0.74625 HYPE`) を毎回送ってしまうのを避けるためです。切り捨てなので、
目標量を超過することは構造的に起こりません。

### 価格の丸め

Hyperliquid の価格グリッドは「有効数字 5 桁以下」かつ「小数点以下 `6 - szDecimals` 桁以下」です。
本ツールはこれに加えて**方向**を制御しています。

- **ロングは切り上げ (ceil)**
- **ショートは切り捨て (floor)**

四捨五入や一律切り捨てにすると、丸めた結果の指値がベストアスク/ベストビッドを跨げなくなり、
IOC 注文が板に届いた瞬間に不発 (即時キャンセル) になります。約定性を維持する方向へ倒しています。

また、ワイヤ形式へ変換する際は末尾のゼロを除去します (`2387.0` → `2387`)。
これは親リポジトリで実際に `badAloPxRejected` を踏んだ実績にもとづく処理です。

### 最低名目金額 ($10) の判定

Hyperliquid には約 $10 の最低名目金額があります。この判定は **mid ではなく実際の注文価格**
に対して、1% の余裕をもたせて行います。

ショートの場合、テイカー指値は mid **より下**に置かれます。mid 換算でちょうど $10.00 になる
サイズが、実際に取引所へ届く価格では $9.96 になり、致命的な `MinTradeNtl` 拒否として
返ってくる — これを実価格で判定することで、全体停止ではなく「そのスライスを skip して繰越」
という軽い処理に変えています。

起動前の検証で 1 スライスがゼロまたは最低金額割れになる場合は、何も送信せずに停止します。
執行中に価格が動いて割れた場合は skip して次スライスへ繰り越します (目標量は累積値なので
繰越は自動的に行われます)。最終スライスでも割れている場合、その残余は本質的に執行不能なので
警告として報告します。

### 丸め落ちは必ず報告する

1 スライスを切り捨てる以上、adjusted 合計が要求量を下回ることがあります。
`szDecimals` が粗い銘柄では差が大きくなります (例: 整数単位の銘柄で 10.5 を 3 スライス
→ adjusted 9)。

adjusted 目標を満たしていれば「完了」ではありますが、単独の `complete` は表示しません。
`complete (against the adjusted target)` と表示し、次の行を必ず添えます。

```
NOTE:            rounding dropped 1.5 of requested 10.5 at pre-flight
```

この NOTE は部分約定や中止の場合にも表示されます。丸め落ちの事実は結果によらず変わらないためです。

## スライスループ

### キャッチアップ方式

各スライスの目標は**累積値**です。

```
target_at_slice(i) = per_slice × i     (最終スライスは adjusted 合計そのもの)
今回の発注量        = target_at_slice(i) − これまでの約定量
```

前のスライスが約定不足だった分は、次のスライスの発注量に自動的に上乗せされます。
逆に約定が先行している場合は発注量がゼロになり、そのスライスは何も送りません。
最終スライスの目標を adjusted 合計に固定することで、丸めの端数もすべて吸収されます。

### 執行ウィンドウは厳格

`--duration` が経過した後は、**最終スライスであっても**注文を出しません。

再試行・板の再取得・約定量の確定処理で遅延は蓄積します。そして最終スライスはキャッチアップ
により、それまでの不足分をすべて背負った**最大サイズ**になりがちです。ここだけ例外にすると、
「その回で最も大きい注文が、指定ウィンドウから最も遠く外れて発火する」という最悪の組み合わせに
なります。期限に達した実行は停止し、未執行分を報告します。通常の実行では最終スライスは
ウィンドウ内に収まります。

### 執行期限の二重防御: `ExecutionDeadline` (ローカル) と `expiresAfter` (取引所側) (Issue #2)

上記の不変条件は、以前はスライス開始時に一度だけ確認されていました。しかしその後に板取得や
再送の照合を `await` するため、期限直前に開始したスライスが、板取得の timeout/retry や
曖昧送信の照合中に期限を越えたあとで（catch-up により最大化した可能性のある）注文を送信
できてしまう抜け道がありました。この抜け道を塞ぐため、責務の異なる 2 つの時計を導入しています。

**`ExecutionDeadline` (ローカル・monotonic)** — `src/twap.rs`。`run_twap` の開始時に
`tokio::time::Instant` ベースで一度だけ構築され、place/reconcile/resend の各層まで渡されます。

- **必ず「送信の直前」に再確認します**: 初回発注の直前、および曖昧送信 (transport failure)
  後の再送の直前の 2 箇所。期限確認をループ先頭で一度行うだけでは、その後の `await`
  (板取得の再試行、`reconcile_by_cloid` の照合ポーリング) の間に期限を越えても検出できません。
- **期限後も許可される操作**: `orderStatus` 照会・cancel は期限後も継続して呼べます (すでに
  発注済みの注文の後始末は止めてはいけないため)。**禁止されるのは新規の place と resend のみ**
  です。
- **板取得・再試行の予算も期限で打ち切ります**: `fetch_fresh_book` に `ExecutionDeadline` を
  渡すと、残り時間が `STALE_BOOK_RETRY_INTERVAL` (1秒) より短い場合は再試行の sleep 自体を
  短縮し、残り時間がゼロならその場で打ち切ります。期限まで 200ms しか残っていない状況で
  再試行予算いっぱい (最大 3 回 × 1秒 = 3秒) を消費させないためです。
- monotonic clock を使う理由: wall-clock の NTP 補正やサスペンドの影響を受けず、
  「送ってよいか」というローカルな意思決定を狂わせないため。

**`expiresAfter` (wall-clock・取引所側)** — `src/client.rs` / `src/eip712.rs` /
`src/signer.rs`。`ExecutionDeadline` の構築時に、同じ瞬間の wall-clock (Unix ms) から
`start + duration` に相当する絶対時刻を計算し、run の実行中ずっと**同じ値**を使い続けます。

- この値は `/exchange` リクエストボディの `expiresAfter` フィールドと、署名対象の EIP-712
  action hash (`action_hash(..., expires_after)`) の**両方に同じ値で**渡されます —
  片方だけ設定してももう片方が一致しなければ、HL 側の署名検証に矛盾が生じます。
  (`tests/exchange_parse.rs` の `place_request_body_carries_the_same_expires_after_used_for_signing`
  がこの一致を mockito 経由で検証しています。)
- 最終スライスや resend を含む、run が送るすべての注文が同じ `expires_after_ms` を使います。
  resend は「新しい期限」を得るのではなく、run 開始時に決まった同じ値を再利用します。
- 目的: ローカルの `ExecutionDeadline` チェックをすり抜けるバグがあっても、HL 自身の
  `expiresAfter` enforcement が独立した第二の防御になります。二重防御であり、
  どちらか一方に依存しない設計です。
- `cancelByCloid` は `expiresAfter` を付けません (`None`) — cancel は期限後も許可される操作
  なので、cancel 自体が期限切れになってはいけないためです。

**責務のまとめ**:

| 概念 | 時計 | 役割 | 期限後の扱い |
|---|---|---|---|
| `ExecutionDeadline` | monotonic (`tokio::time::Instant`) | ローカルな「送信してよいか」の判定 | place/resend 禁止、status 照会/cancel は継続可 |
| `expiresAfter` | wall-clock (Unix ms) | HL 側の独立した expiry enforcement | HL が自身の時計で判定 (ローカルとは独立) |

これは既存の `--expire-after` フラグ (Issue #8、待機フェーズの打ち切り) とは**別の概念**です。
`--expire-after` はトリガー待機中 — まだ 1 枚も発注していない段階 — の打ち切りであるのに対し、
`ExecutionDeadline` はトリガー発火後、スライスが実際に送信されるフェーズの期限です。混同しない
でください。

### クロックずれの検証 (Issue #2)

`expiresAfter` は wall-clock (Unix ms) に依存するため、実行ホストの時計が Hyperliquid の
サーバー時計とずれていると、ローカルが意図した期限と HL が実際に enforce する期限が食い違います。
これを防ぐため、**live モード (read-only ではない実運用) のみ**、トリガー発火直後に取得した
`ValidatedMarketSnapshot` のサーバータイムスタンプ (`server_ts_ms`) とローカル wall-clock を
比較します。

- **チェックのタイミング**: トリガー待機の**前**ではなく、トリガーが発火した**直後**
  (`main.rs`、`println!("Triggered: {reason}")` の後、スライスループ開始前のサイジング用
  スナップショット取得と同じ箇所) です。以前の実装 (コミット `9986b46`) は待機開始前に
  専用の `l2Book` 呼び出しを追加していましたが、これは `--start-after` のみのトリガー
  (価格条件なし) が「期限が来るまで一切ネットワークを叩かない」という不変条件
  (Issue #6/#8、`trigger.rs` の `time_only_trigger_fires_after_deadline_without_network`)
  を破っていたため、Finding 3 でこの位置に移動しました。
- 価格トリガーで発火した場合もタイムアウト/`--start-after` で発火した場合も、**トリガー成立
  を判定するために既に取得済みのスナップショット**からタイムスタンプを読むだけで、
  クロックずれ検証専用の追加 `l2Book` 呼び出しは一切発生しません。
- 許容範囲: `|ローカル時刻 − サーバー時刻| <= 5000ms` (`MAX_CLOCK_SKEW_MS`、`src/twap.rs`)。
- 超過時は **fail-closed** — スライスループ開始前に中止し、注文は一切送信しません。
  エラーメッセージで NTP 同期の確認を促します。
- read-only / paper モードでは検証しません。何も署名しないため、ローカル時計が狂っていても
  `expiresAfter` が実際に送信されることはなく、実害がないためです。
- **運用上の前提**: 実行ホストは NTP でシステムクロックを同期しておく必要があります。
  クラウド VM (AWS/GCP 等) では既定で有効なことが多いですが、自前のホストで動かす場合は
  `timedatectl` 等で NTP 同期の状態を確認してください (詳細は `docs/DEVELOPMENT.md`)。

### 板の検証: `ValidatedMarketSnapshot`

`/info l2Book` の生レスポンスは、価格トリガーのポーリング・pre-flight サイジング・
各スライスの直前という 3 箇所すべてで、境界（`ValidatedMarketSnapshot::validate`）を
通ってから初めて `OrderBook` から検証済みスナップショットに変換されます。以前はこの 3 箇所が
バラバラに (トリガーは無検証、pre-flight とスライスだけ鮮度チェックのみ) 板を扱っており、
古い交差板だけでトリガーが成立したまま直後の新鮮な板でサイジングが進む、という不整合が
起こり得ました。検証内容は以下の通りで、**すべて同じポリシーです**:

- レスポンスの `coin` がリクエストした銘柄と一致すること
- best bid / best ask が両方とも存在し、価格・数量が正の値であること
- `best_bid <= best_ask` (交差していないこと)
- レベルが HL の約束通りの並び順であること (bid は降順、ask は昇順)
- `--max-book-age-ms` (既定 3000ms) より古くないこと — **`0` はこの鮮度チェックのみを
  無効化します**。銘柄一致・正値・非交差・並び順の検証と、次項の未来スキュー許容は
  `0` でも常に適用されます
- タイムスタンプがローカル時刻より未来方向に 2000ms (固定) を超えていないこと

古い板・不正な板は最大 3 回まで (1 秒間隔) 再取得を試み、それでも検証を通らなければ
ハードストップします。

なお、板のタイムスタンプがローカル時刻よりわずかに未来 (2000ms 以内) の場合は「新鮮」として
扱います。軽度のクロックずれを許容するためです。これを超える未来タイムスタンプは、クロックずれ
ではなく不正なレスポンスの可能性が高いため、`--max-book-age-ms` の値に関わらず拒否します。

## エラー処理

最も重要な区別は次の 3 つです。

| 種類 | 挙動 | 理由 |
|---|---|---|
| `/info` の通信エラー | 指数バックオフで再試行 (1s → 2s → 4s) | 読み取り専用なので再試行のコストがない |
| `/exchange` の通信エラー | **再試行しない**。cloid で照合して復旧 | nonce により注文は冪等ではない (後述) |
| 取引所の拒否 | **再試行せず即時停止** | 取引所は既に判断を下している。再送は二重約定のリスク |

### 曖昧な送信の照合 (`/exchange` reconciliation)

注文は nonce に対して署名され、Hyperliquid は本文を受け取った時点で nonce を消費します。
つまり `POST /exchange` が **HL に届いた後**で失敗した場合 (タイムアウト、応答の消失)、
同じ署名済み本文を再送しても nonce 切れで拒否されるだけで、しかも元の注文は約定している
かもしれません。素朴な「3 回再試行」では、実際には約定した注文を「失敗」と報告してしまいます。

そこで `/exchange` へのリクエストは **1 回だけ送信**し、**cloid を冪等キー**として復旧します
(cloid は署名前に自分で決めるため、応答が失われても手元に残ります)。

1. 曖昧な失敗が起きたら、master アカウントで `/info orderStatus` に cloid を照会する
2. **HL が注文を持っている** → その状態を採用。再送はせず、約定は 1 回だけ計上する
3. **`unknownOid` が返る** → 注文は届いていないので、**新しい nonce で再署名**して再送
   (最大 2 回まで。毎回、再送前に照合を挟む)
4. **照合自体が失敗し続ける** → 停止し、結果が不明であることを明示する。
   どちらかに決め打ちすると二重約定のリスクがあり、それは取り消せない

cancel の失敗は致命的ではありません。その後の `orderStatus` 照会が真実を確定させるためです。

### 終端ステータスのみを採用する

約定量として採用するのは **終端ステータス** (`filled`, `canceled`, `rejected` など) のときだけです。

`open` のままの注文は次の 1 ミリ秒で追加約定しうるため、その時点の部分約定数を最終値として
採用すると約定量を過小に見積もり、以降のすべてのスライスが**過剰発注**になります
(キャッチアップが「まだ足りない」と誤認するため)。`open` の場合は再試行を続け、
それでも終端に至らなければ安全側に倒して停止します。

### IOC が板に残った場合

IOC 注文が想定外に板に残った (resting) 場合は、キャンセルした上で `/info orderStatus` を
照会し、実際に何枚約定したかを確定させます。このとき約定価格は**指値ではなく HL が報告する
`avgPx`** を採用します (指値は「最悪の価格」なので、平均価格レポートが歪むため)。

約定量を確定できない場合は推測せずに停止します。ゼロと仮定すると次のスライスで過剰発注に
なり、超過ポジションは取り消せないためです。

### 拒否メッセージの分類

Hyperliquid は構造化されたエラーコードを返さず、自由文のメッセージを返します。
本ツールは代表的なものを部分文字列で分類し、対処可能なメッセージに変換します。

| 分類 | 判定キーワード (大文字小文字を無視) | 表示 |
|---|---|---|
| 証拠金不足 | `insufficient margin` | 入金するか `--usd`/`--size` を減らしてください |
| 最低名目金額割れ | `mintradentl`, `minimum` | `--usd`/`--size` を増やすか `--slices` を減らしてください |
| 未分類 | 上記以外 | HL の生メッセージをそのまま表示 |

分類できなかった場合も**停止する点は同じ**です。分類は原因究明を助けるためのものであり、
安全性の判断には使っていません。

## userRole 照会によるマスター解決

本番実行時 (ドライランでは行いません) の起動時に、`HL_AGENT_PK` から導出したアドレスで
`/info userRole` を照会します。目的は 2 つです。

1. **未登録の鍵を早期に検出する** — Hyperliquid は認可されていない API ウォレットからの
   署名アクションを拒否します。最初の注文で判明するより、起動時に止まる方が安全です
2. **マスターアカウントを解決する** — HL は Agent の注文を**マスター配下**に記録するため、
   `/info orderStatus` はマスターアドレスで照会する必要があります。Agent のアドレスで
   照会すると、実在する注文に対して `unknownOid` が返ります。約定量の復旧処理はこれを
   「約定ゼロ」と誤読し、以降のすべてのスライスで過剰発注してしまいます

実際の mainnet API で応答形状を確認済みです。

```
POST /info {"type":"userRole","user":"<agent_addr>"}
  → {"role":"agent","data":{"user":"0x<master>"}}

POST /info {"type":"userRole","user":"<master_addr>"}
  → {"role":"user"}

POST /info {"type":"orderStatus","user":"<master>","oid":<未知>}
  → {"status":"unknownOid"}
```

照会結果が `agent` 以外だった場合は、確認できた role を表示して起動を中止し、何も送信しません。

## EIP-712 署名

署名コア (`src/eip712.rs` / `src/signer.rs`) は親リポジトリ `diff-old-new/executor` から
**そのまま移植**したものです。Hyperliquid Python SDK に対してバイト単位でクロスチェック済みで、
その検証ベクタ (10 件) も一緒に移植しています。

重要な性質:

- msgpack は**名前付きマップ**でシリアライズします (`rmp_serde::to_vec_named`)。
  配列形式にすると action_hash が変わり、署名が無効になります
- 構造体の**フィールド順序が意味を持ちます**。並べ替えると署名が壊れます
- EIP-712 ドメインは mainnet / testnet で同一です (`chainId=1337`, `verifyingContract=0x0`)。
  ネットワークの違いは `Agent.source` の `"a"` / `"b"` だけで表現されます
- `--network` はエンドポイント URL と `Agent.source` を**同時に**切り替えるため、
  両者が食い違うことは構造的に起こりません

詳細は [DEVELOPMENT.md](DEVELOPMENT.md) を参照してください。
